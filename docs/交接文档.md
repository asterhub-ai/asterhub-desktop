# AsterHub Desktop handoff

English | [中文](交接文档.zh.md)

This page records the current DSH Desktop product contracts and handoff state. Source, tests and the linked package references remain authoritative for exact behavior.

## 1. Product boundary

AsterHub is an Electron Desktop application with a local Node Host and bundled Web client. The DSH fork is maintained on `asterhub`; the upstream repository is a source of selected fixes, not the product configuration authority.

The Desktop Host pins its built-in model route to provider `sub2api`, model `aster`, and `https://xapi.fans/v1` before any profile or home patch mounts. The account control endpoint is fixed to `https://xapi.fans/api/v1`. A signed-in model key is stored in the Host credential record `asterhub-account/model-api-key`; it is not read from `SUB2API_API_KEY`, `.env`, or process environment and is never returned to the Client.

Session model selection, old Session state, `settings.yaml`, Workflow child options, subagent options, and `llm/stream` middleware cannot make a built-in DSH model request use another provider/model route. The adapter profile and base URL are rebuilt from the application-owned Host route. A local administrator or installed Host plugin remains a trusted-capability boundary: the application route lock does not sandbox hostile in-process code or prevent direct network requests made by such code.

## 2. Plugin and MCP operations

The app Plugins page is a separate signed curated catalogue. The Host verifies the Ed25519 signature over the raw payload bytes, expiry, monotone revision, entry identity, exact package version and SHA-512 integrity. Entries may point to a same-origin HTTPS tarball under `/releases/`; install requests bind that URL and the other signed facts. The Host checks the exact root importer, package name/version and lockfile integrity before activation. Curated installs run with dependency scripts disabled. Revision 2 is live and lists GenOffice CLI (`@asterhub/genoffice-cli@0.11.0-asterhub.1`) and Aster IM (`@asterhub/aster-im@4.32.0`).

The user separately authorized conversation-driven plugin and MCP lifecycle operations from arbitrary sources. Standard, PTC and Creator expose the existing `plugin_manager` tool, with its per-call Host approval and build-script approval behavior preserved. An MCP can be installed as a DSH bundle containing `@deepseek-ai/dsh-mcp-client`; the shipped `adding-mcp-server` skill explains stdio and Streamable HTTP bundle setup and the existing bundle enable/disable/remove flow. No standalone raw-command/URL MCP manager is provided.

The Plugin Manager protects the core model, credential and sandbox-policy composition rows from ordinary bundle lifecycle operations. Installed Host plugins still execute with Host-user privileges, outside the workspace sandbox.

## 3. Desktop updates and catalog service

`services/asterhub-catalog/` is deployed on the German host at `https://asterhub.xapi.fans`. It serves the signed catalogue and immutable plugin tarballs from `data/releases/`; the public verification key is pinned in `apps/desktop-host/src/catalog-trust.ts`, while the Ed25519 private key remains outside the repository in the local AsterHub signing-key directory. The Node service's release route maps to `data/releases/`. The separate electron-updater feeds and mandatory-update release metadata remain unconfigured; the policy route still returns only the safe no-force response.

New Desktop builds package `https://asterhub.xapi.fans` as their update-feed and policy origin. The existing release uploader still publishes feed YAML, binaries, and blockmaps to Tencent COS. The Nginx example proxies `/dsh-desk/feeds/` and `/dsh-desk/bin/` read-only to the same bucket; the Node service handles metadata APIs and curated plugin tarballs. The catalogue's `artifactUrl` install contract is implemented in this worktree, but a signed Desktop build carrying that Host/Client code has not been packaged or published. Older installed builds cannot install these hosted tarballs through the catalogue.

## 4. Validation in the current worktree

The affected Host and Client TypeScript project graph has been checked. Focused Vitest coverage exercised route locking, account credential-record handling, Session/Workflow/subagent paths, plugin lifecycle, curated signature/install matching, shipped preset skill visibility, and Desktop feed selection. The service's Node tests cover the signed catalogue, fail-closed behavior, no-force policy, static feed mapping and traversal refusal. Docker Compose and a packaged/signed Desktop update have not been verified here.

The account gate now provides registration: the form reads public sign-up settings, sends an email verification code through the authentication service, submits registration, and uses the returned account session to bind the local key. An unsigned Windows portable directory build renames the Electron executable to `AsterHub.Runtime.exe` and creates an approximately 24 KiB `AsterHub.exe` launcher; total installed payload size is unchanged. The local `apps/desktop/.desktop-build/local-packages/AsterHub-0.1.6-alpha.2-win-x64-portable.zip` is an unsigned ZIP of 431,060,925 bytes. It contains the email-registration UI and excludes BaiduSync upload temporaries. No signed installer or public release was produced; registration end-to-end and installed startup remain unqualified.

## 5. Deployment boundary

The curated catalogue and release routes are active on the existing `asterhub.xapi.fans` service. The catalog container was rebuilt to map `/releases/<file>` to `data/releases/<file>`; no DNS, Cloudflare tunnel, certificate, or other product service was changed. Future catalogue publications must increase the revision, sign the exact payload bytes with the external Ed25519 key, upload tarballs first, then publish `catalog.json` and `catalog.sig`. Do not claim a Desktop app update until a signed Desktop package containing the `artifactUrl` support is published through the separate release process.
