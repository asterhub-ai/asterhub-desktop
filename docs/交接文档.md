# AsterHub Desktop handoff

English | [中文](交接文档.zh.md)

This page records the current DSH Desktop product contracts and handoff state. Source, tests and the linked package references remain authoritative for exact behavior.

## 1. Product boundary

AsterHub is an Electron Desktop application with a local Node Host and bundled Web client. The DSH fork is maintained on `asterhub`; the upstream repository is a source of selected fixes, not the product configuration authority.

The Desktop Host pins its built-in model route to provider `sub2api`, model `aster`, and `https://xapi.fans/v1` before any profile or home patch mounts. The account control endpoint is fixed to `https://xapi.fans/api/v1`. A signed-in model key is stored in the Host credential record `asterhub-account/model-api-key`; it is not read from `SUB2API_API_KEY`, `.env`, or process environment and is never returned to the Client.

Session model selection, old Session state, `settings.yaml`, Workflow child options, subagent options, and `llm/stream` middleware cannot make a built-in DSH model request use another provider/model route. The adapter profile and base URL are rebuilt from the application-owned Host route. A local administrator or installed Host plugin remains a trusted-capability boundary: the application route lock does not sandbox hostile in-process code or prevent direct network requests made by such code.

## 2. Plugin and MCP operations

The app Plugins page is a separate signed curated catalogue. The Host verifies the Ed25519 signature over the raw payload bytes, expiry, monotone revision, entry identity, exact package version and registry integrity. Install requests bind the catalogue revision and all signed package facts; the Host requires the root importer to resolve the exact direct dependency and verifies that referenced registry package integrity before activation. Curated installs run with dependency scripts disabled. The catalogue starts empty and unavailable until a current signed payload is published.

The user separately authorized conversation-driven plugin and MCP lifecycle operations from arbitrary sources. Standard, PTC and Creator expose the existing `plugin_manager` tool, with its per-call Host approval and build-script approval behavior preserved. An MCP can be installed as a DSH bundle containing `@deepseek-ai/dsh-mcp-client`; the shipped `adding-mcp-server` skill explains stdio and Streamable HTTP bundle setup and the existing bundle enable/disable/remove flow. No standalone raw-command/URL MCP manager is provided.

The Plugin Manager protects the core model, credential and sandbox-policy composition rows from ordinary bundle lifecycle operations. Installed Host plugins still execute with Host-user privileges, outside the workspace sandbox.

## 3. Desktop updates and catalog service

`services/asterhub-catalog/` contains a read-only Node/Docker/Nginx deployment scaffold for the signed catalogue, electron-updater feed files and the existing mandatory-update policy response. The policy route currently returns only the safe no-force response. The signed starter catalogue is empty; its public verification key is pinned in `apps/desktop-host/src/catalog-trust.ts`, while the Ed25519 private key is kept outside the repository in the local AsterHub signing-key directory.

New Desktop builds package `https://asterhub.xapi.fans` as their update-feed and policy origin. The existing release uploader still publishes feed YAML, binaries, and blockmaps to Tencent COS. The Nginx example proxies `/dsh-desk/feeds/` and `/dsh-desk/bin/` read-only to the same bucket; the Node service handles metadata APIs. Existing installed builds keep the feed URL embedded in their package. Cloudflare DNS and the German-host service have not been changed or deployed, so the public hostname is not yet an active AsterHub release endpoint.

## 4. Validation in the current worktree

The affected Host and Client TypeScript project graph has been checked. Focused Vitest coverage exercised route locking, account credential-record handling, Session/Workflow/subagent paths, plugin lifecycle, curated signature/install matching, shipped preset skill visibility, and Desktop feed selection. The service's Node tests cover the signed catalogue, fail-closed behavior, no-force policy, static feed mapping and traversal refusal. Docker Compose and a packaged/signed Desktop update have not been verified here.

## 5. Deployment boundary

Before public activation, inspect the existing Cloudflare DNS record for `asterhub.xapi.fans`, reconcile it with the German host's current Nginx/TLS route, and preserve the current xapi.fans services. The Host's `rover` account cannot access Docker at the moment; no permission change, `sudo`, Cloudflare mutation, DNS rewrite, certificate change, SSH deployment or service start has been performed. Service deployment and DNS activation still require the appropriate host access and a final action-time approval.

Do not treat the prepared scaffold as a deployed service. Do not publish a Desktop update until signed platform feed metadata and immutable, signed artifacts have been placed on the configured origin and qualified.
