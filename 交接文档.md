# AsterHub Desktop handoff

English | [中文](交接文档.zh.md)

This page records the current AsterHub Desktop product contracts and handoff state. Repository paths below are relative to the `AsterHub-reference` project root; source, tests and package references remain authoritative for exact behavior.

## 1. Product boundary

AsterHub is an Electron Desktop application with a local Node Host and bundled Web client. The DSH fork is maintained on `asterhub`; the upstream repository is a source of selected fixes, not the product configuration authority.

The Desktop Host pins its built-in model route to provider `sub2api` and `https://xapi.fans/v1`; no model is preselected, and users choose a model and effort from the key’s `/v1/models` catalog before any profile or home patch mounts. The account control endpoint is fixed to `https://xapi.fans/api/v1`. A signed-in model key is stored in the Host credential record `asterhub-account/model-api-key`; it is not read from `SUB2API_API_KEY`, `.env`, or process environment and is never returned to the Client.

Session model selection, old Session state, `settings.yaml`, Workflow child options, subagent options, and `llm/stream` middleware cannot switch the built-in provider, endpoint, or credential source; users may select account-catalog models through the model menu. The adapter profile and base URL are rebuilt from the application-owned Host route. A local administrator or installed Host plugin remains a trusted-capability boundary: the application route lock does not sandbox hostile in-process code or prevent direct network requests made by such code.

## 2. Plugin and MCP operations

The app Plugins page is a separate signed curated catalogue. The Host verifies the Ed25519 signature over the raw payload bytes, expiry, monotone revision, entry identity, exact package version and SHA-512 integrity. Entries may point to a same-origin HTTPS tarball under `/releases/`; install requests bind that URL and the other signed facts. The Host checks the exact root importer, package name/version and lockfile integrity before activation. Curated installs run with dependency scripts disabled. The repository contains signed catalogue revision 3 with GenOffice CLI (`@asterhub/genoffice-cli@0.11.0-asterhub.1`) and Aster IM (`@asterhub/aster-im@4.32.0`); the catalogue service is not deployed, so clients cannot yet fetch or install these entries from the public origin.

The user separately authorized conversation-driven plugin and MCP lifecycle operations from arbitrary sources. Standard, PTC and Creator expose the existing `plugin_manager` tool, with its per-call Host approval and build-script approval behavior preserved. An MCP can be installed as a DSH bundle containing `@deepseek-ai/dsh-mcp-client`; the shipped `adding-mcp-server` skill explains stdio and Streamable HTTP bundle setup and the existing bundle enable/disable/remove flow. No standalone raw-command/URL MCP manager is provided.

The Plugin Manager protects the core model, credential and sandbox-policy composition rows from ordinary bundle lifecycle operations. Installed Host plugins still execute with Host-user privileges, outside the workspace sandbox.

## 3. Desktop updates and catalog service

`services/asterhub-catalog/` is a read-only Node/Docker/Nginx deployment scaffold and is not connected to Cloudflare, the German host, or production DNS. The repository contains a signed revision 3 catalogue with GenOffice and Aster IM; `data/desktop/latest.json` has no version or download URLs, and no plugin tarballs are staged under `data/releases/`. The public verification key is pinned in `apps/desktop-host/src/catalog-trust.ts`, while the Ed25519 private key remains outside the repository in the local AsterHub signing-key directory. The policy route returns only the safe no-force response.

New Desktop builds package `https://asterhub.xapi.fans` as their update-feed and policy origin. The existing release uploader still publishes feed YAML, binaries, and blockmaps to Tencent COS. The Nginx example proxies `/dsh-desk/feeds/` and `/dsh-desk/bin/` read-only to the same bucket; the Node service handles metadata APIs and curated plugin tarballs. The catalogue's `artifactUrl` install contract is implemented in this worktree, but a signed Desktop build carrying that Host/Client code has not been packaged or published. Older installed builds cannot install these hosted tarballs through the catalogue.

## 5. Deployment boundary

The catalogue service, DNS, and release routes are not deployed from this checkout. Do not claim the public origin is active until the service and proxy are installed and verified. Future catalogue publications must increase the revision, sign the exact payload bytes with the external Ed25519 key, upload tarballs first, then publish `catalog.json` and `catalog.sig`. Do not claim a Desktop app update until a signed Desktop package containing the `artifactUrl` support is published through the separate release process.
