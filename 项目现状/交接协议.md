# 交接协议（多 Agent 并行 · 插件化跟上游）

> 适用：在 AsterHub 仓库协作的 OMP / ZCode / Codex 与其它 Agent，以及真人。
> 目标：多 Agent 可并行接力且不踩踏；额度切断不丢断点；长期跟 DSH 上游而不漂成另一套产品。
> 本目录是协作辅助设施，不是 AsterHub 产品功能。

## 0. 战略锚点（常驻，所有认领之上）

1. **保绿**：已落地的自研能力在 Windows Desktop/Web 采用路径上保持可用。
2. **插件化**：自研功能与必要修改尽量以插件/扩展缝合，少改 DSH 核心，便于持续跟上游。
3. **择需跟上游**：对照 DSH 差距只吸收**已证实的产品必要项**；不追求提交数追平、不因上游测试红扩大修复面。
4. **仅 Windows 产品维护**：保留 Git Bash 与远端 SSH；不把非 Windows 专属宿主清零当目标。

任何任务若与上述四点冲突，先停下来改任务卡，再继续。

## 1. 角色：用户只说自然语言

- 用户不跑命令、不写台账。分派/询问/停止一律自然语言。
- Agent 收到任务后默认：`brief`（若接手）→ `claim` → 干活 → 随时 `checkpoint` → 离场 `release --next`。
- 进度询问：Agent 跑 `status`/`brief` 后用自然语言转述，不把命令甩回用户。

## 2. T0：用户手动指令高于一切

- 「停下 / 释放 / 不要认领 / 暂停」等负向指令为 T0：当轮立刻 `release` 全部认领，并清空内部待办，不得延后。
- **严禁臆测恢复**：`ok`、会话续聊、系统重试不等于开工许可；必须带**任务号或明确业务目标**才可再 claim。

## 3. 三条铁律

1. **开工先认领**：改共享文件前 `claim`，声明 owner、`--files`（相对仓库根）、TTL。活跃认领文件清单不得重叠。临时项用 `BUG-xxx` / `AUX-xxx` / `WAIT-xxx` / `UP-xxx` / `KEEP-xxx` / `PLUGIN-xxx` / `SHIP-xxx`。
2. **checkpoint 永远先于继续**：每完成有意义一步就 `checkpoint`（`--next` 必须写到可执行命令级）。额度紧张时先落 checkpoint。`check` 将「认领后从未 checkpoint」判违规。
3. **离场必释放**：`release` 必须带 `--next`；TTL 内无活动视为断线，他人可接管（记 `tookOverFrom`）。

## 4. 看板与数据分层（2026-11-03 重设计）

| 层 | 文件 | 信任 |
|---|---|---|
| 权威状态 | `status-data.js` | 人工/主会话核实后 |
| 协作协议 | `交接协议.md`（本文） | 规则 |
| 细节叙事 | `交接文档.md` | 过程/证据链/决策理由；**不复述看板现值** |
| 自报台账 | `journal/<task>.jsonl` | 不可信自报；关单仍须核实后改看板 |
| 原始证据 | `.local-workspace/` 等 | 原始 |

### 4.1 任务卡必填字段

- `id` / `title` / `track` / `category` / `priority` / `status` / `label` / `detail` / `acceptance`
- 跟上游相关时再填：`upstreamRelation`（`none|already|evaluate|absorb|defer|exclude`）、`pluginizable`（`yes|partial|no|n/a`）、`blocksRelease`（bool）
- 等人/授权：`waitOn`（`user|auth|external`）且 `status=waiting_user`

### 4.2 状态机（关单卫生）

| status | 含义 | Agent 可否 claim |
|---|---|---|
| `ready` | 可开工的窄切片 | 是 |
| `partial` | 已开始、仍有 Agent 步骤 | 是（先 brief） |
| `evaluating` | 评估/对照中，结论未出 | 是 |
| `waiting_user` | 只等人或明确授权 | **否** |
| `blocked` | 被其它卡或外部阻塞 | 否（除非扫阻塞） |
| `verified` | 已关单 | 否 |
| `pending` | 尚未解锁 | 否 |

`handoff.mjs status` 仍把非 `verified` 列为待办；Agent **不得认领** `waiting_user` / `pending` / `blocked`。

### 4.3 轨道（替代旧 W0–W11 战役叙事）

- `WAIT`：用户动作 / 授权门
- `KEEP`：自研采用路径保绿
- `PLUGIN`：自研侵入插件化
- `UP`：上游差距评估与定向吸收
- `SHIP`：精确安装包与交付

并行原则：**一张卡 = 一个可并行窄切片**（文件面或语义面尽量不与其它活跃卡重叠）。大卡必须拆子卡；父卡只做汇总门，子卡全 `verified` 后父卡才关。

### 4.4 打包门禁（收窄）

禁止最终打包的条件，**仅当**存在 `blocksRelease: true` 且状态不是 `verified` 的任务（已证实、影响当前候选的缺陷或门禁）。
评估卡、`waiting_user`、P2 长期路线、未解锁 `pending` **默认不阻塞打包**。
打包前：`node 项目现状/handoff.mjs status`，留存「无 blocksRelease 未关单」证据。签名/对外发布另需用户明确授权。

### 4.5 仓库与版本边界（保留）

- AsterHub 与 AsterHive 严格分仓；本仓分支不用 `asterhive/` 前缀。
- 对外产品版本独立于 DSH；DSH 版本/提交只作内部基线映射。
- 不向看板/journal 写入凭据；不碰 `~/.asterhub/`、真实项目 `.aster/`、私人配置。

## 5. 命令速查（Agent 执行）

```sh
node 项目现状/handoff.mjs status
node 项目现状/handoff.mjs brief <TASK>
node 项目现状/handoff.mjs claim <TASK> --owner <ID> --files <paths...> [--ttl-minutes 240]
node 项目现状/handoff.mjs checkpoint <TASK> --owner <ID> --next "..." [--done ...] [--evidence ...]
node 项目现状/handoff.mjs note <TASK> --owner <ID> --text "..."
node 项目现状/handoff.mjs release <TASK> --owner <ID> --next "..." [--reason ...]
node 项目现状/handoff.mjs check
```

接手最小读取：`brief <task>` 一条；不要先通读整份交接文档。禁止手编 journal JSONL。
