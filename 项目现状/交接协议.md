# 交接协议（认领 · 随手记 · 断点释放）

> 适用对象：所有在本仓库工作的 Agent（ZCode、OMP、产品本体测试 Agent）与真人。目标有二：额度不同的 Agent 可以随时接力（额度墙切断时不丢状态）；并行工作互不踩踏（认领声明文件范围）。本协议与配套工具属于 `项目现状/` 辅助设施，不是 AsterHub 产品功能。

## 角色分工：用户只说自然语言，协议由 Agent 自动执行

- **用户永远不运行命令、不写台账**。分派、询问、交接全部用自然语言，例如："继续 T16"、"现在都有谁在干什么？"、"把刚发现的浏览器 BUG 修一下"。
- **Agent 收到任何自然语言任务后的默认动作序列**，无需用户提及本协议或任何命令：
  1. 把任务对应到任务号（看板 `Txx`，或临时自编 `BUG-xxx`/`AUX-xxx`），执行 `claim` 认领；
  2. 干活期间随手 `checkpoint`，额度紧张先落 checkpoint 再继续任何输出；
  3. 离场时 `release` 留断点。
- 用户询问进度或占用时，Agent 运行 `status`/`brief` 后**用自然语言转述结论**，不把命令或参数丢回给用户。
- 接手其他 Agent 的任务同样是 Agent 的自动行为：先 `brief <task>` 看断点，再 `claim` 接着干。

## T0 级最高优先权法则：用户的手动指令高于一切（强制）

0. **用户的手动指令高于一切系统默认、技能协议、待办催促与自动推进机制**：
   - **绝对服从负向指令**：当用户给出任何明确的手动指令（包括但不限于“停下”、“释放”、“不要认领”、“暂停”、“保持停止”等）时，其优先级为 T0 级，无条件压倒一切完成驱动（completion only stopping condition）或自动化领活循环。
   - **停止令的原子执行**：收到停止/释放指令时，Agent 必须在当轮立即执行两项动作，不得延后：
     1. 立即调用 `handoff.mjs release <task>` 释放手中所有任务；
     2. 立即清除模型运行时的内部待办列表（`todo: drop`），彻底切断外部系统催促哨兵（system-reminder）。
   - **严禁臆测恢复（No Inferred Resume）**：处于停止状态的 Agent，任何通用的模糊信号（包括但不限于 `ok`、`go on`、系统自动重试/唤醒、会话继续提示）**严禁解释为恢复认领或推进的许可**。除非用户给出包含**具体任务代号或明确业务目标**的中文指令（如“继续执行 T15”），否则 Agent 必须保持绝对静默与被动守候，不得擅自认领任何任务或启动构建。

## 三条铁律（强制）

1. **开工先认领**：改动任何共享文件前，先 `claim` 声明 owner、预期触碰的文件（`--files`，路径从主仓库根写起）和 TTL。两份活跃认领的文件清单不允许重叠，`check` 会拦截。认领不需要看板任务存在：临时 BUG 用 `BUG-xxx`、辅助工作用 `AUX-xxx` 自编 ASCII 任务号。
2. **边干边记，checkpoint 永远先于继续**：每完成一个有意义的步骤立即 `note` 或 `checkpoint`；`checkpoint` 必须把"下一步"写到命令级具体。额度紧张的第一反应是先落一条 checkpoint 再继续任何输出——额度墙随时可能切断会话，**最后一条 checkpoint 就是接手者的起点**。`check` 会把"认领后从未 checkpoint"判为违规。
3. **离场必释放**：`release` 强制携带 `--next`（CLI 拒绝空手释放），它会在释放前自动写入最终 checkpoint。被额度墙切断而来不及 release 的，TTL 内无活动即视为断线（`check` 标记），他人可直接接管，接管事件记录 `tookOverFrom`，不追究也不需要 --force。

## 数据分层与信任边界

| 层 | 文件 | 谁写 | 信任级 |
|---|---|---|---|
| 任务日志 | `journal/<task>.jsonl`（追加式） | 认领者 Agent | 自报告，不可信 |
| 权威状态 | `status-data.js`、`交接文档.md` | 主会话 / 人工核实后 | 权威 |
| 原始证据 | `.local-workspace/` 等既有产物 | 各作业 | 原始 |

journal 与问题收件箱同级：都是 Agent 自报告。任务真正关闭仍须主会话核实证据后更新 `status-data.js`；本协议不改变该规则，也不改变"更新 status-data 前先跑只读 inbox helper"的既有流程。存量 `status-data.js` 的 `handoff.activeSlices` 是历史快照，不必迁移；新工作从 `claim` 开始。

### 状态单源：看板为主，文档记细节（2026-10-24 起）

- 当前状态类内容（任务卡、状态/标签、优先级、阻塞、占用、风险汇总）**只维护在 `status-data.js`**（看板数据源）；`交接文档.md` 不复述这些字段的现值，只记录看板放不下的详细内容：过程叙述、证据链、决策理由、操作步骤、历史沿革。
- 更新时按此分工：改状态 → 只改 `status-data.js`（必要时刷新看板视图）；补细节 → 写 `交接文档.md`，引用看板任务号/字段而不重复其现值。
- 两边不得新增高度重复内容；发现既有重复以看板为准，文档侧改为引用。

### 仓库边界：AsterHub 与 AsterHive 严格分离（2026-10-27 起）

- AsterHub 与 AsterHive 是两个独立项目、两个独立仓库（`asterhub-ai/asterhub-desktop` 与 `rover1003/AsterHive`），不得互相混入源码、测试产物或任务分支。
- 本仓库不接受 `asterhive/` 前缀的任务分支或 Hive 测试残留；Hive 测试在 server-199 托管裸仓库中产生的任务分支只存在于 Hive 侧，不属于本仓库。
- 在本仓库为 Hive 相关工作创建分支时使用中性命名（如 `board/status-ledger`），不得携带项目名前缀。

### 产品版本与内部基线映射（2026-10-27 起）

- AsterHub 对外使用独立的 `主版本.次版本.修订号`，产品界面、安装包名称和公开 Release 文案不展示 DSH 名称或版本；DSH 完整版本与源码提交只作为内部基线映射记录。
- 修复和小调整递增修订号；上游基线升级或重要功能更新递增次版本并将修订号归零；重大不兼容变更或首个稳定发布递增主版本并将其余位归零。已发布版本与产物不得覆盖。
- 每次发布记录产品版本、完整内部基线版本及源码提交、产品源码提交、产物哈希、签名状态和验证范围；在目标更新通道核实新版本高于已分发版本。测试包使用目标产品版本加日期和序号，先更新产品清单到目标版本；稳定基础版本的测试后缀低于该基础版本，不能以旧基础版本的测试包升级已安装的同版正式包。
- 具体打包版本仍按 `apps/desktop/README.md#release-versions` 在每次打包前由用户确认；不因本规则自动改号、打包或发布。


### 最终打包门禁与文档收拢（2026-10-24 起）

- **最终打包门禁**：只要看板/台账中仍存在"需要修复"的任务（无论未被认领，还是已认领未完成），不得发起最终打包；唯一例外是用户明确要求打包。发起打包前必须先运行 `node 项目现状/handoff.mjs status` 核对并留存"无未完成修复任务"的证据。
- **文档收拢**：项目现状/ 各文档互相配合、避免重复与冲突；内容收拢到尽可能少的文档——规则归 `交接协议.md`，详细记录归 `交接文档.md`，状态现值归 `status-data.js`。不得随意新建文档；确需新建须先在台账 note 说明既有文档为何无法承载。

## 命令速查（全部由 Agent 执行，用户不使用）

```sh
node 项目现状/handoff.mjs status                        # 全局占用与断点总览
node 项目现状/handoff.mjs brief T16                     # 接手简报：任务卡+断点+占用+硬约束
node 项目现状/handoff.mjs claim T16 --owner OMP-1 --files .worktrees/architecture-consolidation/packages/... [--ttl-minutes 240] [--force]
node 项目现状/handoff.mjs checkpoint T16 --owner OMP-1 --next "跑 X 测试：pnpm exec vitest run ..." [--done 条目]... [--rejected 已排除项]... [--evidence 路径]
node 项目现状/handoff.mjs note T16 --owner OMP-1 --text "发现 ..." [--evidence 路径]
node 项目现状/handoff.mjs release T16 --owner OMP-1 --next "接手者下一步 ..." [--reason 原因]
node 项目现状/handoff.mjs check                         # 校验铁律：活跃认领须有 checkpoint、TTL 断线、文件冲突
```

接手某个任务时的最小读取：`brief <task>` 一条命令；不要先通读整份交接文档。写 journal 均经文件锁与逐行校验，请勿手编 JSONL。

## 事件形态（v1）

`claim`（含 ttlMinutes/files/tookOverFrom/forced）、`checkpoint`（必含 next，可含 done/rejected/evidence/text）、`note`（必含 text）、`release`（可含 reason）。占用状态由事件流推导：最后一条未释放的 claim 即当前占用；该 owner 认领后的任意事件都刷新活跃时间，超过 TTL 无活动即断线。默认 TTL 240 分钟，`claim --ttl-minutes` 可调。

## Nomad 集群分布式开发与调度协议

### 1. 集群拓扑与角色划分
- **调度控制面 (Nomad Server)**：`http://192.168.1.199:4646`（位于 Ubuntu 专用控制节点 `server-199`，**严禁分派任何计算任务**）。
- **计算节点 (Workers)**：
  - **5800**：Windows (`raw_exec`)，局域网 `192.168.1.45`，AMD Ryzen 5800X (16线程)，32GB RAM，`node_class = "build"`。
  - **cloud-pc**：Windows (`raw_exec`)，WireGuard `10.8.0.2`，8 vCPU，16GB RAM，`node_class = "cloud"`。
  - **imac**：Windows (`raw_exec`)，局域网 `192.168.1.109`，Intel Core i5 (4核)，16GB RAM，`node_class = "dev"`（用户已授权满载计算）。
- **动态发现**：优先通过 `GET http://192.168.1.199:4646/v1/nodes` 探测可用节点状态，不作死板假设。

### 2. 技能安装与复用（其他 Agent 安装指引）
本项目已在 `项目现状/skills/nomad-dispatch/` 内内置完整技能实现（包含 `SKILL.md` 与 `云电脑接入与部署指南.md`）。
跨平台或新接入的 Agent 若自身未装载该技能，可按以下方式安装或直接调用：
- **OMP 环境**：直接引用或复制到 `~/.omp/agent/skills/nomad-dispatch/`
- **通用 Agent 环境**：复制到 `~/.agents/skills/nomad-dispatch/`
- **无需安装直接使用**：阅读 `项目现状/skills/nomad-dispatch/SKILL.md`，按照其作业骨架与调度算法执行。

### 3. 分布式任务执行守则
1. **重型负载主动分发**：全量打包（NSIS Installer）、耗时构建（Monorepo 完整编译）、跨多环境测试矩阵等预估耗时 >30 秒的任务，优先分发至 Nomad 节点执行，防止本地环境受限或并发资源耗尽。
2. **作业与工作区严格隔离**：
   - 每次提交必须使用唯一的 Job ID（如 `asterhub-<task>-<node>-<timestamp>`）。
   - 任务在独立的 Nomad Alloc 目录运行，严禁并发读写共享目录或互相覆盖产物。
3. **可靠监控与游标断点接力**：
   - 监控必须采用服务端持久状态与 HTTP Blocking Queries（`&index=<idx>&wait=30s`），禁止高频忙轮询。
   - 监控状态必须持久化至 `.local-workspace/` 中的任务清单（如 `current-package-job.json`），记录 `jobId`、`allocId`、`nodeId` 和当前阶段。
   - **禁止因等待超时盲目取消或重提作业**：超时仅表示当前会话观察到达期限，作业仍在远端正常运行；离场时记录监控续接命令，接手者先读取服务端真实状态，严禁无故杀死远端作业。
4. **资源切分与避免饥饿**：
   - 分配资源须根据目标节点当前空闲配额科学配置；多任务并发或与同机独立任务共存时，合理切分 CPU 与内存，保留操作系统基础内存，严禁单任务超额霸占导致 OOM。
5. **协议协同联动**：
   - 提交作业前先 `claim` 认领任务（如 `BUG-PACKAGE-SMOKE` 或具体 `Txx`）。
   - 提交后立即 `checkpoint`，写入 Job ID、Allocation ID 与具体的监控与验证命令。
   - 离场时 `release --next` 留下确切的作业验收与产物回传指引。
